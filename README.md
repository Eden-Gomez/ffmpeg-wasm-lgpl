# ffmpeg-wasm-lgpl

An **LGPL-only** FFmpeg WebAssembly core for audio, built reproducibly from pinned upstream
sources, with everything needed to check it yourself.

This is the build that [weconvertit.com](https://www.weconvertit.com) runs in the browser for
its audio tools. It is published here as a separate, replaceable component, with its exact
corresponding source.

## What it is

| | |
|---|---|
| FFmpeg | 5.1.10, unmodified ([release tarball](https://ffmpeg.org/releases/ffmpeg-5.1.10.tar.xz)) |
| Toolchain | Emscripten 3.1.40 (`emscripten/emsdk` image pinned by digest) |
| Threads | none: single-threaded, no SharedArrayBuffer, no COOP/COEP headers needed |
| External libraries | LAME 3.100 (MP3), libvorbis 1.3.7 + libogg 1.3.6 (Vorbis), zlib 1.3.1 |
| Not included | `--enable-gpl`, `--enable-nonfree`, `--enable-version3`, x264, x265, fdk-aac, libpostproc, avdevice, network |
| Output | `dist/ffmpeg-core.js` + `dist/ffmpeg-core.wasm` (16.7 MB): an Emscripten `MODULARIZE` module, `createFFmpegCore`, exporting `FS` and `callMain` |

All of FFmpeg's native decoders, demuxers, filters and muxers stay enabled, except those that
are GPL-only. Encoders include MP3 (LAME), Vorbis (libvorbis), and FFmpeg's native AAC, ALAC,
FLAC, Opus and PCM. The full lists are in `dist/decoders.txt`, `encoders.txt`, `demuxers.txt`,
`muxers.txt` and `filters.txt`, generated by the binary itself.

5.1 is the newest FFmpeg series whose `ffmpeg` CLI builds without threads. 6.0 and later require
them, which in WebAssembly means SharedArrayBuffer and cross-origin isolation for the whole site.

## Why it exists

[ffmpeg.wasm](https://github.com/ffmpegwasm/ffmpeg.wasm) is a widely used project, and it is
what made FFmpeg in the browser practical. This repository exists because of it, not against it.

Its prebuilt cores are configured for video, with x264 and x265. That makes them GPL builds, and
the project says so. Here is what's published, checked on 2026-11-22:

- `@ffmpeg/core` and `@ffmpeg/core-mt` 0.12.x are configured with
  `--enable-gpl --enable-libx264 --enable-libx265`. Their npm `license` field is
  `GPL-2.0-or-later`. It was changed from MIT in
  [PR #686](https://github.com/ffmpegwasm/ffmpeg.wasm/pull/686) after
  [#685](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/685) was reported, and has been on npm
  since 0.12.8. The project's
  [FAQ](https://github.com/ffmpegwasm/ffmpeg.wasm/blob/main/apps/website/docs/faq.md) explains
  that `@ffmpeg/core` follows "the same licenses as FFmpeg and its external libraries". The
  `@ffmpeg/ffmpeg` wrapper is MIT.
- The older `@ffmpeg/core` / `@ffmpeg/core-st` 0.11.x cores were also configured with
  `--enable-nonfree --enable-libfdk-aac`. For that configuration, the binary's own `ffmpeg -L`
  prints: *"This version of ffmpeg has nonfree parts compiled in. Therefore it is not legally
  redistributable."* The npm metadata for those versions says MIT.

GPL is a legitimate choice for a video toolkit. But a site or app whose own code isn't
GPL-licensed, and which only needs audio, needs a core configured the way FFmpeg's
[legal page](https://ffmpeg.org/legal.html) puts first in its checklist: *"Compile FFmpeg
without "--enable-gpl" and without "--enable-nonfree"."* This repository is one such core,
with every input pinned and the result checkable by anyone.

Open discussions on the topic:
[#107](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/107),
[#427](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/427),
[#902](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/902).

## How to check any ffmpeg.wasm build's licence

FFmpeg records how it was configured inside the binary. Each of these methods works on any
ffmpeg.wasm core, this one or another.

**1. Read the configure line out of the `.wasm`, without running it.** This works for single-
and multi-threaded builds and for any wrapper:

```sh
node tools/check-licence.mjs node_modules/@ffmpeg/core/dist/umd/ffmpeg-core.wasm
```
```
  configuration: --target-os=none --arch=x86_32 ... --enable-gpl --enable-libx264 --enable-libx265 ...
  flags of interest: --enable-gpl --enable-libx264 --enable-libx265
  licence FFmpeg's configure assigns to this configuration: GPL version 2 or later
```
The exit code is 0 for an LGPL configuration, 1 if `--enable-gpl` or `--enable-nonfree` is
present, and 2 if no configure line is found. There are no dependencies. Without Node, run
`strings ffmpeg-core.wasm | grep -- --target-os` and read the line yourself.

**2. Ask the binary.** `-version` prints the configure line, and `-L` prints the licence. With
the ffmpeg.wasm 0.12 API in a browser:

```js
ffmpeg.on('log', ({ message }) => console.log(message));
await ffmpeg.exec(['-L']);
```

With this core in Node (see [Usage](#usage)), use `ffmpeg.callMain(['-L'])`. For this build it prints:

```
ffmpeg is free software; you can redistribute it and/or
modify it under the terms of the GNU Lesser General Public
License as published by the Free Software Foundation; either
version 2.1 of the License, or (at your option) any later version.
```

**3. Read the build script** of whoever published the core, and compare it with what the binary
reports. To read the result, use FFmpeg's own `configure --help`:

```
  --enable-gpl             allow use of GPL code, the resulting libs
                           and binaries will be under GPL [no]
  --enable-nonfree         allow use of nonfree code, the resulting libs
                           and binaries will be unredistributable [no]
```

## Build it with Docker

Requirements: Docker with BuildKit (any recent Docker Desktop or Engine).

```sh
git clone https://github.com/Eden-Gomez/ffmpeg-wasm-lgpl
cd ffmpeg-wasm-lgpl
docker build --no-cache --output type=local,dest=rebuild .
```

What the build does:

1. Starts from `emscripten/emsdk:3.1.40@sha256:c1e807a6…` (pinned by digest) and installs
   `pkg-config=0.29.2-1ubuntu3` (pinned by exact version).
2. Checks every tarball in `sources/` against `SHA256SUMS`, then builds zlib, LAME, libogg,
   libvorbis and FFmpeg (`build.sh`). It fixes `SOURCE_DATE_EPOCH`, `TZ=UTC` and `LC_ALL=C`.
3. Runs `smoke.js` on the result. It writes `version.txt`, `buildconf.txt`, `license.txt` and the
   component lists. It **fails the build** if the configure line contains `--enable-gpl`,
   `--enable-nonfree`, `--enable-version3`, `libx264`, `libx265` or `libfdk`, or if `-L` doesn't
   report the LGPL. It then encodes one second of audio to MP3, WAV, M4A, AAC, OGG and FLAC.

CI ([`.github/workflows/build.yml`](.github/workflows/build.yml)) runs the same build on every
push and pull request. It fails on any of those flags, on a non-LGPL `-L`, or if the result
isn't byte-identical to `dist/`.

## Verify the build is bit-for-bit reproducible

After the build above:

```sh
(cd rebuild && sha256sum -c ../dist/SHA256SUMS)
for f in version.txt buildconf.txt license.txt decoders.txt encoders.txt demuxers.txt muxers.txt filters.txt; do
  cmp rebuild/$f dist/$f && echo "$f identical"
done
```

Expected:

```
ffmpeg-core.js: OK
ffmpeg-core.wasm: OK
```

This was checked on 2026-11-22 with Docker Engine 29.4.3 (linux/amd64, 16 CPUs), using
`docker build --no-cache`. The build took 9 min 12 s. `ffmpeg-core.js`, `ffmpeg-core.wasm` and
all eight evidence files were byte-identical to `dist/`. The CI workflow repeats the same check
on GitHub's runners for every push.

To check that `sources/` are the genuine upstream releases, download them again and compare
them with `SHA256SUMS`:

```sh
mkdir upstream && cd upstream
curl -LO https://ffmpeg.org/releases/ffmpeg-5.1.10.tar.xz
curl -LO https://downloads.sourceforge.net/project/lame/lame/3.100/lame-3.100.tar.gz
curl -LO https://downloads.xiph.org/releases/ogg/libogg-1.3.6.tar.xz
curl -LO https://downloads.xiph.org/releases/vorbis/libvorbis-1.3.7.tar.xz
curl -LO https://github.com/madler/zlib/releases/download/v1.3.1/zlib-1.3.1.tar.xz
sha256sum -c ../SHA256SUMS
```

## Usage

The core is a plain Emscripten module: `createFFmpegCore()` resolves to an instance with `FS`
(the in-memory filesystem) and `callMain(args)` (runs the `ffmpeg` CLI and returns its exit
code). **Use one instance per command**, because FFmpeg keeps process-global state between calls.
**Pass `-nostdin`**, or in Node ffmpeg will wait on stdin for keypresses.

### Node

```js
const fs = require('fs');
const createFFmpegCore = require('./dist/ffmpeg-core.js');

(async () => {
  // One instance per command: FFmpeg keeps global state between calls.
  const ffmpeg = await createFFmpegCore({ printErr: () => {} });
  ffmpeg.FS.writeFile('in.wav', fs.readFileSync('in.wav'));
  const code = ffmpeg.callMain(['-nostdin', '-i', 'in.wav', '-c:a', 'libmp3lame', '-q:a', '2', 'out.mp3']);
  if (code !== 0) throw new Error('ffmpeg exited with ' + code);
  fs.writeFileSync('out.mp3', ffmpeg.FS.readFile('out.mp3'));
})();
```

### Browser, with the included worker

`worker/audio-worker.js` is the production worker from weconvertit.com, unchanged. It compiles
the wasm once and creates a fresh instance for each job. It reports download and encode
progress, and mounts large `File`s without copying them into wasm memory. Its comments mention
the site's file names, which you can ignore.

Serve `dist/ffmpeg-core.js` and `dist/ffmpeg-core.wasm` from one folder (for example
`/ffmpeg-core/`, with `.wasm` as `application/wasm`), and the worker from anywhere:

```js
const worker = new Worker('/audio-worker.js?core=/ffmpeg-core/'); // trailing slash required

worker.onmessage = ({ data }) => {
  if (data.type === 'progress') console.log(Math.round(data.ratio * 100) + '%');
  if (data.type === 'error') console.error(data.error);
  if (data.type === 'done') {
    const mp3 = new Blob([data.bytes], { type: 'audio/mpeg' });
    // ... offer it for download, play it, etc.
  }
};

const input = await file.arrayBuffer(); // a File from <input type="file">
worker.postMessage(
  { id: 1, inputData: input, inputName: 'in.wav', outputName: 'out.mp3',
    ffmpegArgs: ['-c:a', 'libmp3lame', '-q:a', '2'] },
  [input],
);
```

The worker adds `-nostdin -y` itself. Input-side options go in `inputArgs` (for example
`['-ss', '30']`), and output-side options go in `ffmpegArgs`. The header comment in the worker
documents the multi-input message form too.

### Replacing the core

The worker and any page that uses it depend only on this interface: a `MODULARIZE` module named
`createFFmpegCore` that exports `FS` and `callMain`. To run with a different or modified FFmpeg
build, build a core with the same interface, put its `ffmpeg-core.js` and `ffmpeg-core.wasm` in a
folder, and point the worker at it with `?core=/your/folder/`.

## Changes to upstream build scripts

- libvorbis: `configure` adds `-mno-ieee-fp` for i686 hosts, and clang (wasm) rejects that flag.
  `build.sh` removes it from the generated configure script with `sed`. No library source file
  is changed.
